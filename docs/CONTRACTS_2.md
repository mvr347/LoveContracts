# Контракты 2.0 и NPC LoveEssential

## Для игрока

Поручения выбираются непосредственно при разговоре с NPC.
ПКМ — квестовый разговор, если этому игроку сейчас нужен этот NPC. Shift+ПКМ — обычная роль NPC, например торговля LoveBrew.
У других игроков профессия NPC продолжает работать. После последнего этапа приоритет разговора исчезает автоматически.

Средние, сложные и одноразовые шаблоны теперь становятся цепочками: принять предложение → обсудить условия → выполнить работу → отчитаться у заказчика.
Простые заказы остаются в обычной ротации. Уже принятые заказы старого формата сохраняются и завершаются прежним способом.
Для цепочек действия до соответствующего этапа не засчитываются. Прогресс, повторяемость и кулдаун сохраняются в SQLite.

## Трактирщик LoveBrew

Добавочный файл `npc_stories.yml` создаётся один раз, без замены пользовательского `npc_quests.yml`.
Встроенная история: контрактник рассказывает о задержке поставки → трактирщик просит хлеб → игрок передаёт 24 хлеба → итоговый разговор и оплата.
Передача изымает обычные предметы из основного инвентаря. Переименованные предметы и предметы с метаданными не принимаются.
При ошибке записи предметы возвращаются. Повторное нажатие и устаревший диалог не продвигают этап повторно.

Настройка привязок:

- `@contractor` использует существующий `npc.key`, настроенный `/lovecontractsadmin npc`.
- `@brew:saloonkeeper_main` находит NPC с меткой `lovebrew.trader=saloonkeeper_main` в выбранном провайдере.
- Для другого продавца замените ID после `@brew:`; для NPC без меток укажите его обычный ключ.
- LoveContracts и LoveBrew должны использовать один NPC-провайдер, обычно `global` с LoveEssential в LoveCore.
- Не нужно создавать второго NPC для квестовой роли. Если трактирщик отсутствует по расписанию, игрок может вернуться позже.

В `npc_quests.yml` и `npc_stories.yml` доступны последовательные `VISIT_NPC`, `VISIT_LOCATION`, `DELIVER_ITEM`, `MINE_MATERIAL`, `CRAFT_ITEM`, `KILL_ENTITY`, `CATCH_FISH`.
У разговорного этапа задаются `target-npc-key`, `description`, `dialogue.text` и `dialogue.options`; подтверждающая опция использует `COMPLETE_STEP`.
Другой NPC, удалённое нажатие и диалог другого этапа не подходят для подтверждения.
Начальные ветки `fearful`, `skeptical`, `friendly` выбираются по LoveCore BehaviorLevels; при отсутствии ветки используется `initial-dialogue`.
Агрессия вызывает осторожность, плохая вежливость — скепсис. Отсутствующий провайдер репутации означает нейтральную реакцию.

Сгенерированные цепочки имеют ID `story_<id шаблона>`. В `contracts.yml` можно задать `story-npc-key` для конкретного заказчика.
Пользовательская история с таким ID в файлах NPC имеет приоритет перед автоматически созданной.
`stories.convert-complex-orders: false` возвращает сложные шаблоны в обычную ротацию.
`/lovecontractsadmin reload` перечитывает также определения цепочек. Не меняйте смысл и порядок этапов уже идущей истории: выпустите новую историю под новым ID.

## Единая доска и конструктор (2026-11-21)

Две доски (обычные контракты и поручения NPC) объединены в одну: вкладки «Обычные», «Цепочки», «От игроков», «Мои»
(`/contracts`, `/pcontract board`, `/pcontract my`). Цепочки видны на доске, их можно взять с неё и бросить; взятие цепочки и
любой отказ идут через окно подтверждения. NPC с несколькими поручениями открывает доску на вкладке «Цепочки» только с его
поручениями. Цепочки собираются в игровом конструкторе `/lovecontractsadmin chains` и хранятся в `chains.yml`; подробности в README.

Провайдер NPC теперь один, LoveEssential: ключ `integrations.npc-provider` удалён, старое значение в конфиге игнорируется с
предупреждением. Числа в `npc-key` и `target-npc-key` — номера NPC LoveEssential.

## Экономика только контрактов

Номиналы LoveCore не меняются: золотая монета стоит 2000 медных единиц.
Новые настройки добавляются при обновлении без перезаписи существующих значений:

```yaml
economy:
  contracts-v2:
    reward-factor: 0.15
    max-reward: 240
    rolling-income-limit: 1800
```

Коэффициент применяется к системным наградам и штрафам после старых коэффициентов и индекса цен; максимум ограничивает итоговую награду, включая модель цен.
Системные заказы и NPC-цепочки используют общий лимит 1800 за любые 24 часа. Полночь и переподключение не сбрасывают его.
Поэтому накопить первую золотую только новыми выплатами контрактов за первые 24 часа нельзя. Прочие источники дохода, уже имеющиеся деньги и заказы игроков не меняются.
Если выплата не помещается в лимит, завершение откладывается целиком. Прогресс сохраняется, штрафа нет. Сдайте готовое задание позже.
Готовый собирательный финальный этап после снятия лимита можно повторно сдать кликом по заказчику.
`rolling-income-limit: 0` отключает ограничение; при настройке сохраняйте `max-reward <= rolling-income-limit`, если лимит включён.
Значения наград показываются в диалоговом меню, а не зашиваются в реплики истории.

## Проверка перед обновлением сервера

Собрать на Java 25: `mvn -B verify` в LoveContracts, LoveEssential и LoveBrew. Нужен доступ к их Maven-репозиториям.
Полная Maven-сборка LoveContracts прошла на Java 25: 114 тестов без ошибок. Проверены JDBC-хранилище, бюджет, кулдауны, формат квестового табло, жизненный цикл его запросов, области целей, связи с достижениями и защита активных определений.
Перед сборкой LoveContracts установите API LoveEssential в локальный Maven-репозиторий, как указано ниже.

На тестовом сервере дополнительно проверить двух игроков одновременно, смену рабочего времени во время разговора,
передачу хлеба с неполным/полным инвентарём, переподключение между этапами, окончание кулдауна и возврат к торговле.
Это необходимые игровые проверки; изолированные тесты не подтверждают поведение на живом Paper.


## Квестовое табло через API LoveEssential

Простые заказы и NPC-цепочки автоматически заменяют стандартное табло временным запросом `ScoreboardService` LE.
Показываются название, текущий этап, задача, счётчик, имя целевого NPC, его текущие координаты и расстояние.
Для передачи вещей счётчик показывает подходящие обычные предметы в инвентаре; сама передача остаётся действием диалога.
Если NPC отсутствует или цель в другом мире, табло явно сообщает об этом.
При нескольких заданиях показывается последнее принятое или затронутое разговором; после его завершения выбирается следующее.
Завершение/отмена последнего задания, выход игрока и отключение LoveContracts освобождают запрос — LE возвращает обычное табло.
Личные настройки табло не перезаписываются, прямого захвата Bukkit scoreboard нет, SQL на таймере табло не выполняется.

`quest-scoreboard.enabled` включает интеграцию, `quest-scoreboard.priority` по умолчанию 20.
Сервис scoreboard в LE должен быть включён. Ограничения LE по миру и авторизации продолжают действовать.
Запрос `force=true` позволяет заменить лично выключенное табло только при разрешённом в LE `scoreboard.overrides.allow-forced`.
Арены и события с более высоким приоритетом сохраняют преимущество. Табло обновляется каждые 5 тиков.

LoveContracts использует зависимость `dev.lovelace:loveessential-api:2.0.0-SNAPSHOT` в scope provided; API не встраивается в JAR.
Перед сборкой из соседних исходников:

```sh
cd /workspace/LoveEssential-
mvn -B -pl api -am install -DskipTests
cd /workspace/LoveContracts
mvn -B verify
```

## Любые персонажи и места

Механизм квестов не привязан к трактирщику. Назначьте актёрам существующих NPC выбранного провайдера:

```yaml
npc-actors:
  herbalist:
    npc-key: herbalist_main
  captain:
    tag-key: settlement.role
    tag-value: captain
```

В `npc-key` заказчика и `target-npc-key` этапов можно использовать `@actor:herbalist` и `@actor:captain`.
Обычные ключи NPC, `@contractor` и совместимая привязка `@brew:<seller-id>` продолжают работать.
Актёр может торговать, иметь свой обычный LE-диалог или действие другого плагина; квест временно перехватывает только соответствующий этап конкретного игрока.
Если у NPC несколько текущих поручений или новые предложения, игрок выбирает тему разговора в общем списке. Выбранное поручение получает фокус на табло. Shift+ПКМ оставляет доступ к обычной роли. Квесты не переписывают профессии, диалоги и определения NPC глобально.

`dialogue.reactions.fearful/skeptical/friendly/neutral` задают варианты реплик и ответов конкретного этапа.
У варианта без `options` наследуются базовые ответы, поэтому смена реплики не делает этап непроходимым.
Можно задать собственные ответы с `NEXT_NODE`, `COMPLETE_STEP`, `CLOSE`; переход ведёт к именованному узлу `dialogues` данной истории.
Это настраиваемые заранее написанные диалоги и действия, а не генерация реплик.

Этап `VISIT_LOCATION` требует `location: {world: world, x: 120, y: 64, z: -80, radius: 8}` и завершается при входе в область.
Такая же `location` у рабочего этапа ограничивает место добычи, крафта или боя; у простого заказа она задаётся в `condition.location`.
Без области обычная задача выполняется в любом месте. Табло показывает адрес и расстояние до заданной области.

В `npc_stories.yml` добавлен отключённый пример `village_remedy_v2`: капитан → травница → болотная тропа → передача ингредиентов → отчёт капитану.
Настройте реальные NPC и координаты, затем поставьте `enabled: true` и выполните `/lovecontractsadmin reload`.
Другие истории можно строить из тех же этапов без изменений Java-кода.
